# IRCE Pipeline Playbook — Replicating Across Verticals
## The pattern for making any bot "conversational"

*Generated: 2026-03-12 by Claude O4.6*
*Based on: proyecto-miche production implementation + scaffold architecture*

---

## The Core Idea

IRCE turns a bot from a **command executor** into a **conversational assistant**.

Without IRCE:
```
User: "vendí 2 jeans"
Bot:  "🤔 No entendí. Usa /fotos, /listo, /help"
```

With IRCE:
```
User: "vendí 2 jeans"
Bot:  "Voy a registrar VENTA: 2x Jeans Azul M = $36.000. Stock: 5→3. ¿Correcto? [✅ Sí] [❌ No]"
```

The difference: **6 layers between input and output**, each with a clear responsibility.

---

## The 6 Layers

```
┌──────────────────────────────────────────────────────────────┐
│  ① INPUT         Capture any input type → normalize to text  │
│  ② COMPREHENSION Classify intent + extract entities          │
│  ③ RESOLUTION    Match entities to real DB records            │
│  ④ CONFIRMATION  Show what will happen, ask permission        │
│  ⑤ EXECUTION     Atomic DB transaction                       │
│  ⑥ RESPONSE      Rich feedback + next steps                  │
└──────────────────────────────────────────────────────────────┘
```

Each layer is **independent** and **replaceable**. You can swap Whisper for another STT in Layer 1, swap regex for a fine-tuned model in Layer 2, swap Supabase for another DB in Layer 5 — the other layers don't care.

## Layer-by-Layer Playbook

### ① Input Capture

**Job:** Accept anything the user throws at you, normalize it to processable data.

| Input Type | Technology | Output | Cost | Latency |
|-----------|-----------|--------|------|---------|
| Text message | Passthrough | `string` | Free | 0ms |
| Voice note | OpenAI Whisper | `string` (transcribed) | $0.006/min | 1-3s |
| Photo(s) | Kimi Vision K2.5 | `JSON` (structured data) | ~$0.01/batch | 20-30s |
| Document (.txt) | File download + read | `string` | Free | <1s |

**Rules:**
- Voice always goes through Whisper, never Kimi (Kimi can't do audio)
- Photos always go through Kimi Vision (async, fire-and-forget)
- Text goes straight to Layer 2
- Always normalize: trim, lowercase for matching, preserve original for display

**Voice correction patterns (Spanish-specific):**
```
"vendidos jeans"  → "vendí dos jeans"   (Whisper merges words)
"bendí"           → "vendí"             (b/v confusion)
"vendido"         → "vendí"             (missing quantity context)
```

**To add a new input type for a new vertical:**
Just add a normalizer function. Everything downstream stays the same.

---

### ② Comprehension (The Hybrid Brain)

**Job:** Understand what the user wants (intent) and extract the relevant pieces (entities).

**Architecture: Regex-first, LLM-fallback.**

```
Input text
    │
    ├──→ Regex Engine (handles 80% of messages)
    │    Cost: $0 | Latency: <50ms
    │    100+ keyword patterns per rubro
    │    Priority-ordered: SELL > ADD_STOCK > QUERY > ...
    │
    │    If confidence >= 0.7 → return result
    │    If confidence < 0.7  ↓
    │
    └──→ Kimi K2.5 LLM (handles 20% of ambiguous messages)
         Cost: ~$0.001 | Latency: ~500ms
         Config: temp=0.6, thinking=disabled, response_format=json_object
         Returns: { intent, confidence, entities }
```

**Why regex first?**
- 80% of retail messages are simple: "vendí 2 jeans", "cuántos quedan", "sí", "no"
- Regex handles these in <50ms with 95%+ accuracy
- Only ambiguous/complex messages need the LLM
- Circuit breaker: if Kimi is down, regex keeps working

**Intent output format (universal across verticals):**
```typescript
interface IntentResult {
  intent: string;           // Rubro-specific intent name
  confidence: number;       // 0.0 - 1.0
  entities: {
    [key: string]: any;     // Rubro-specific extracted data
  };
  method: 'regex' | 'llm'; // Which engine resolved it
}
```

**To add intents for a new vertical:**
1. Define the intent list (what can users ask/do?)
2. Write regex patterns for the obvious keywords
3. Write a Kimi prompt for the ambiguous cases
4. Add to the router dispatch table

### ③ Resolution (The Detective)

**Job:** Map extracted entity names to real database records.

**Algorithm:**
```
User said: "jeans azul"
DB has:    "Jeans Azul Marino Talla M" (id: uuid-123)
           "Jeans Azul Marino Talla L" (id: uuid-456)
           "Jeans Negro Talla M"       (id: uuid-789)

Scoring:
  uuid-123: name("jeans")=+50, color("azul")=+30 → 80
  uuid-456: name("jeans")=+50, color("azul")=+30 → 80
  uuid-789: name("jeans")=+50, color("negro")=0  → 50

Result: [uuid-123 (80), uuid-456 (80), uuid-789 (50)]
Disambiguation needed: two products tied at 80
```

**Score thresholds:**
- `> 90` with single match → auto-confirm (high confidence)
- `75 - 90` or multiple matches → show options to user
- `< 75` → "No encontré ese producto. ¿Quisiste decir...?"

**Weight configuration per rubro:**

```typescript
// Retail: name matters most, then visual attributes
const RETAIL_WEIGHTS = { name: 50, color: 30, size: 20 };

// Real estate: location matters most, then type and price
const REALESTATE_WEIGHTS = { commune: 50, property_type: 30, price_range: 20 };

// Automotive (future): brand+model is king
const AUTO_WEIGHTS = { brand: 40, model: 30, year: 20, color: 10 };

// Services (future): service name is everything
const SERVICE_WEIGHTS = { service_name: 70, professional: 30 };
```

**To add resolution for a new vertical:**
1. Define which fields matter for matching
2. Assign weights (total = 100)
3. Write the DB query (always filter by `tenant_id` + `is_active`)
4. Plug into the resolver with the weight config

**Future upgrade path:** pgvector embeddings replace keyword matching. "jeans oscuro" → embedding → nearest neighbor → "Jeans Azul Marino" (semantic match, no exact word overlap needed).

### ④ Confirmation (The Safety Net)

**Job:** Show the user exactly what will happen before any destructive operation.

**Rules matrix:**

| Operation | Confirm? | Why |
|-----------|----------|-----|
| SELL (deduct stock) | Always | Destructive — can't un-sell |
| ADD_STOCK | Always | Changes inventory counts |
| DELETE | Always | Removes product |
| RECTIFY | Always | Modifies historical records |
| QUERY (read stock) | Never | Read-only, no side effects |
| SEARCH | Never | Read-only |
| ADD_BATCH > 10 items | Yes | Large operation, verify intent |
| ADD_BATCH ≤ 10 items | No | Normal operation |

**Confirmation message format:**
```
[Operation icon] Voy a registrar [OPERATION]:
📦 [Entity details with resolved names]
💰 [Financial impact if applicable]
📊 [State change: "Stock: 5 → 3"]

¿Es correcto? [✅ Sí] [❌ No]
```

**Implementation:** Inline keyboard buttons with callback_data encoding:
```
callback_data: "confirm:SELL:uuid-123:2"  → Yes
callback_data: "cancel:SELL:uuid-123"     → No
```

The confirmation state lives in the callback_data itself — no session storage needed for simple operations. For multi-step flows (rectify, conversational add), use `active_sessions` table.

**To add confirmation for a new vertical:**
Just define which intents need confirmation (use the matrix above as template) and write the message template for each.

---

### ⑤ Execution (The Accountant)

**Job:** Execute the confirmed operation atomically with full traceability.

**Rules:**
1. Every write operation is a transaction (BEGIN/COMMIT/ROLLBACK)
2. Every write operation gets an operation_id (#V001, #L001, #R001)
3. Every write operation is traceable (who, what, when, tenant)
4. Idempotency: check `update_id` before processing (prevent double-execution from Telegram retries)

**Transaction pattern:**
```typescript
const { data, error } = await supabase.rpc('execute_sale', {
  p_tenant_id: tenantId,
  p_product_id: productId,
  p_quantity: quantity,
  p_created_by: telegramUserId,
});
// RPC = server-side function = atomic transaction
// Handles: stock update + sale insert + counter increment
```

**Operation ID format:**
```
#V001 = Sale (Venta) #1
#V002 = Sale #2
#L001 = Batch (Lote) #1
#R001 = Rectification #1
```

Counter lives in `operation_counters` table per tenant per operation type.

**To add execution for a new vertical:**
1. Define the DB tables for the operation (e.g., `appointments` for services)
2. Write the atomic transaction (RPC or multi-step with rollback)
3. Define the operation_id prefix letter
4. Wire into the executor dispatch

---

### ⑥ Response (The Narrator)

**Job:** Tell the user what happened and suggest what to do next.

**Format:**
```
[Status icon] [Result headline]
[Key data points]
[blank line]
[Next actions as text commands or buttons]
```

**Examples per vertical:**

```
# Retail — after sale
✅ Venta #V001 registrada
💰 Total: $36.000
📦 Stock Jeans Azul M: 5 → 3
¿Algo más? /rectificar  /stock  /caja

# Real estate — after search
🏠 3 propiedades encontradas en Ñuñoa:
1. Depto 3D2B — 4.500 UF (Venta)
2. Casa 4D3B — 8.200 UF (Venta)
3. Depto 2D1B — $450.000/mes (Arriendo)
/ver 1  /ver 2  /ver 3

# Services (future) — after booking
✅ Cita agendada
📅 Jueves 13 Mar, 15:00
💇 Corte + Barba con Juan
📍 Av. Providencia 1234
/cancelar  /reagendar
```

**To add responses for a new vertical:**
Write the format template. That's it — the data comes from Layer 5's execution result.

## Recipe: Adding IRCE to a New Vertical

When you create a new rubro_type (e.g., `automotive`, `services-booking`, `restaurant`):

### Step 1: Define Intents (30 min)
List what users can DO via the bot. Example for `services-booking`:
```
BOOK        — "quiero una hora para corte"
CANCEL      — "cancelar mi cita del jueves"
RESCHEDULE  — "cambiar al viernes"
QUERY       — "qué horas hay disponibles?"
CONFIRM     — "sí" / "dale"
CANCEL_OP   — "no" / "cancelar"
```

### Step 2: Write Regex Patterns (1 hour)
For each intent, list the Spanish keywords:
```typescript
const BOOKING_PATTERNS = {
  BOOK: ['reservar', 'agendar', 'hora para', 'quiero una', 'necesito'],
  CANCEL: ['cancelar cita', 'anular', 'no voy a ir'],
  RESCHEDULE: ['cambiar hora', 'mover cita', 'reagendar', 'otra hora'],
  QUERY: ['horas disponibles', 'qué horas', 'cuándo puedo', 'agenda'],
};
```

### Step 3: Define Entity Weights (15 min)
```typescript
const BOOKING_WEIGHTS = { service_name: 70, professional: 30 };
```

### Step 4: Write Command Handlers (2-4 hours)
One handler per destructive intent. Read-only intents can be inline.

### Step 5: Wire Into Router (15 min)
Add the rubro to the dispatch table in `nlp-router.ts`.

### Step 6: Add to Webhook (10 min)
The webhook for the new vertical calls `classifyIntent()` before the "no entendí" fallback. ~10 lines of code.

**Total for a new vertical IRCE: ~4-6 hours** (assuming the core engine from Phase 1 exists).

## Cost Structure

| Component | Cost | When |
|-----------|------|------|
| Regex classification | $0 | 80% of messages |
| Kimi K2.5 intent (text) | ~$0.001/msg | 20% of messages |
| Kimi K2.5 Vision (photos) | ~$0.01/batch | Photo analysis only |
| Whisper (voice) | $0.006/min | Voice notes only |
| Supabase queries | Included in plan | Every message |

**For a tenant doing 100 messages/day:**
- 80 regex ($0) + 20 Kimi ($0.02) + 5 voice ($0.03) + 2 photo batches ($0.02) = **~$0.07/day = ~$2.10/month**

Negligible. The IRCE pipeline pays for itself by making the product actually usable.

## What This Playbook Does NOT Cover

- **pgvector semantic search** — That's Layer 3 upgrade, documented in `Future-pgvector-memory-system.md`
- **Multi-turn conversations** — Requires session state management, is handler-specific
- **Fine-tuning models** — Not needed until 1000+ daily messages per vertical
- **WhatsApp channel** — Different input API, same IRCE pipeline once text is extracted
- **Web UI equivalent** — The same intent engine could power a web chat widget (future)

*IRCE is not a library — it's a pattern. The pattern is: understand first, confirm second, execute third, narrate always. Every vertical follows the same flow, just with different intents, different entities, and different transaction logic.*

*The regex handles the 80%. The LLM handles the 20%. The confirmation handles the trust. The atomic execution handles the safety.*

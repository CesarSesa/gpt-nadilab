# VERTICAL LEGO TEMPLATE v2.1

Standard blueprint for any Nadistudio vertical. One file per rubro.
Each section is a block. A complete vertical has all blocks filled.

Version: 2.1 | Author: Secretary (auditor) + Nadi (architect) | Date: 2026-03-18
Supersedes: v2.0 (2026-03-07)

Updates in v2.1:
- Added IRCE Intent Layer as optional vertical component
- Added operation_counters pattern for transactional verticals
- Added circuit breaker + rate limiter as standard infra
- Added start_date/end_date API conventions and next_operation_id RPC
- Added cron jobs as reusable vertical component

## 1. IDENTITY

| Field | Value |
|-------|-------|
| rubro_type | `'{rubro_type}'` (as stored in `tenants.rubro_type`) |
| vertical directory | `app/admin/[vertical]/{vertical_name}/` |
| middleware mapping | `'{rubro_type}'` cookie value maps to `'{vertical_name}'` directory |
| demo tenant slug | e.g. `demo-moda`, `demo-inmo` |
| bot | Telegram bot name + webhook route |
| public storefront | URL pattern + main entity (products, properties, etc.) |
| **irce_enabled** | `true` / `false` — does this vertical use natural language intents? |

Notes:
- `rubro_type` is the DB value. `vertical_name` is the directory name. They may differ
  (e.g. `retail-clothing` maps to `retail/`, `real-estate` maps to `real-estate/`)
- One rubro = one bot = one webhook route = one admin directory
- **IRCE is optional** — slash-command-only bots are valid for simple verticals

## 5. BOT

### 5.1 Core webhook

| Component | Detail |
|-----------|--------|
| Webhook route | `/api/bot/webhook/{bot_name}` |
| Processor route | `/api/bot/process` (shared, maxDuration 300) |

| **Rate limiter** | 10 req/min + 30 req/hour per user (§42) |
| **Circuit breaker** | 3 failures → 60s cooldown for Kimi API (§41) |

### 5.2 IRCE Intent Layer (Optional)

If `irce_enabled: true`, implement these components:

| Component | File | Purpose |
|-----------|------|---------|
| Intent Engine | `lib/bot/intents/{rubro}.ts` | Regex + Kimi LLM classification |
| Entity Resolver | `lib/bot/resolver/{rubro}.ts` | Fuzzy matching to DB records |
| Confirmation Builder | `lib/bot/confirmation.ts` | Format confirmation messages |
| Operation Executor | `lib/bot/executor/{rubro}.ts` | Atomic transactions + audit log |
| Session Manager | Uses `active_sessions` table | Persist conversation state |

**Intent classification order** (immutable):
```
1. Check active_sessions FIRST (continue conversation)
2. Intent classification (regex → LLM fallback)
3. Entity resolution (fuzzy matching)
4. Confirmation (if destructive operation)
5. Execution (atomic)
6. Response (rich feedback + next steps)
```

**Intents to implement** (examples per rubro):
- Retail: `SELL`, `ADD_STOCK`, `QUERY`, `RECTIFY`, `SEARCH`
- Real-estate: `SEARCH`, `SCHEDULE_VISIT`, `ADD_LEAD`, `QUERY`
- Services: `BOOK`, `CANCEL`, `RESCHEDULE`, `QUERY`

### 5.3 Kimi Vision config

| Setting | Value | Rationale |
|---------|-------|-----------|
| Model | kimi-k2.5 | cost-effective |
| Temperature | 0.6 | balanced creativity/accuracy |
| Thinking | disabled | performance (halves latency) |
| Response format | `json_object` | structured extraction |

### 5.4 Rubro-specific prompt variables

List what Kimi extracts for this vertical:
- (e.g. retail: category, brand, color, size, condition, has_tags, suggested_price)
- (e.g. real-estate: property_type, operation, bedrooms, bathrooms, sqm, commune, price)

Fields Kimi CAN detect from photos vs fields that require manual input.

### 6.1 Circuit Breaker (§41)

Protects against Kimi API cascading failures.

```typescript
const circuitState = { failures: 0, state: 'CLOSED', lastFailure: 0 };

async function callWithCircuitBreaker<T>(fn: () => Promise<T>): Promise<T> {
  if (circuitState.state === 'OPEN') {
    if (Date.now() - circuitState.lastFailure > 60_000) {
      circuitState.state = 'HALF_OPEN';
    } else {
      throw new Error('Circuit breaker OPEN — IA temporalmente no disponible');
    }
  }
  // ... (see Ref-IRCE.md for full implementation)
}
```

**States**: `CLOSED` (normal) → `OPEN` (fast-fail, 60s cooldown) → `HALF_OPEN` → back to `CLOSED` or `OPEN`.

### 8.5 Operation ID Generation (RPC)

For transactional verticals, use the `next_operation_id` RPC pattern:

```sql
-- RPC function in Supabase
CREATE OR REPLACE FUNCTION next_operation_id(
  p_tenant_id UUID,
  p_prefix TEXT  -- 'V' for sales/ventas, 'I' for inquiries, etc.
) RETURNS TEXT AS $$
DECLARE
  v_count INTEGER;
  v_id TEXT;
BEGIN
  UPDATE operation_counters
  SET count = count + 1
  WHERE tenant_id = p_tenant_id AND prefix = p_prefix
  RETURNING count INTO v_count;
  
  IF v_count IS NULL THEN
    INSERT INTO operation_counters (tenant_id, prefix, count)
    VALUES (p_tenant_id, p_prefix, 1)
    RETURNING count INTO v_count;
  END IF;
  
  RETURN '#' || p_prefix || LPAD(v_count::TEXT, 3, '0');
END;
$$ LANGUAGE plpgsql;
```

**Usage**:
```typescript
const { data: operationId } = await supabase.rpc('next_operation_id', {
  p_tenant_id: tenantId,
  p_prefix: 'V'  // Results in #V001, #V002, etc.
});
```

**Prefix conventions**:
- `V` = Venta/Sale
- `L` = Lote/Batch
- `I` = Inquiry/Consulta
- `R` = Rectification
